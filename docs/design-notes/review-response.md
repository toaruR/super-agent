# レビューへの回答 — 主張の撤回と訂正

- 日付: 2026-08-06
- 対象: `docs/spec.md` v3 / `docs/design-notes/scoring.md` の「92点合格」
- 結論: **「92点合格」を撤回する。** 現状は「中心命題のみ N=1 で実証、周辺設計は未実証」が正確。

---

## 1. 経緯

人間のレビュアから、主に「検証の標本数が1件しかない」「自己採点である」という批評を受けた。
このうち**自己採点**の指摘は本設計自身の規律（§6.1「Reviewer は Implementer と別ベンダー」）に
反しており、これを設計書自身に適用していなかったのは**一貫性の欠如**である。

そこで **codex（本設計の著者とは別ベンダー）に独立レビューを依頼**した。

- 簡報: §5.6 の方針通り、`docs/spec.md` 全文を埋め込み（27,128 バイト）
- 権限: read-only
- 出力: JSON スキーマで強制
- 指示: 「実際に検証されたのは 16行1本と合成単体テストのみ」という事実を明示した上で、
  それを超える主張を挙げさせた

### 独立レビューの判定

| 項目 | 結果 |
|---|---|
| **verdict** | **`unsound`** |
| 過大主張 | **26件** |
| 構造的欠陥 | **18件**（うち severity=high **8件**） |

**人間のレビュアの指摘は正しく、かつ独立レビューはそれより厳しかった。**

## 2. 認める指摘（反論しない）

### 2.1 「実証済み」は書きすぎ — 全面的に認める

文書中に「実証済み/実測済み」が **9箇所**あった。実体は:

| 主張していたこと | 実際にやったこと |
|---|---|
| S2「実証済み」 | 16行の fizz.py **1本**。CVE は手動の `python fizz.py` で代替 |
| S4「5ケース実証済み」 | `adjudicate.py` に**合成入力**を渡した単体テスト。**LLM も CVE も CLI も不関与** |
| S1「実測済み」 | 疎通のみ。台帳も YAML 宣言の解釈も**未実装** |
| S3 / S5 / S6 | **一度も実行していない** |

とくに **S4 は悪質**だった。純 Python の関数に辞書を渡しただけのものを、
「裁定規則が機能することの実証」として提示していた。これは統合動作の検証ではない。

**訂正**: §10 の表を ✅/⚠/❌ の3段階に書き換え、「**製品コードは1行も無い**」と明記した。

### 2.2 「偽failは構造的に発生しない」— 撤回

独立レビューの指摘: CVE 故障・依存欠落・証拠取り違え・出力解析失敗・裁定規則のバグなど、
**別経路の偽fail が残る**。「発生しない」には形式証明も網羅テストも無い。

さらに鋭い指摘: **「CVE は環境依存を無くしたのではなく、依存先を1箇所に集約しただけ」**。
これはその通りで、集約先が壊れれば全タスクが止まる（かつ CVE は単一なのでボトルネックにもなる）。

**訂正**: §7.2 に「消えたのは**レビュアの実行環境に起因する偽fail という1経路だけ**」と範囲を限定して明記。

### 2.3 acceptance の質が天井 — 最も重要な指摘。認める

人間・独立レビューの**両方が独立に指摘**した（＝相関の低い2者が同じ結論に達した）。

> `exit 0` は正しさを意味しない。空のテスト・常に成功するテスト・要件を検証しないテストも通る。
> 「正しさ」の天井は Decomposer が書く acceptance の質で決まり、**CVE はそこを解決していない**。

これは設計の中心主張への直撃である。私は「判定の信用」を解いたと書いたが、正確には
**「判定を環境から独立させた」だけ**で、「何を検証すべきか」の妥当性には手をつけていない。

**訂正**: §7.2 に「既知の欠陥」節を追加し、**未解決であることを明記**した。

### 2.4 証拠なき指摘の破棄は正当な指摘も殺す — 認める

設計上の懸念・セキュリティの匂い・保守性の問題は acceptance の exit code に現れない。
P3 を機械適用すると握りつぶす。**「判定の環境独立性」と「指摘の網羅性」のトレードオフを、
前者に全振りしていた**という自覚が無かった。

**訂正**: 暫定緩和策（`advisory` 枠）を §7.2 に記載。ただし未実装であることも明記。

### 2.5 簡報埋め込みと経済性の衝突 — 認める（実測が裏付ける）

今回の独立レビュー自体が証拠になった。`docs/spec.md` 全文の埋め込みで簡報は **27KB**。
16行のレビューで13.8万トークン（E-5）だったことを踏まえると、
数百〜数千行の差分では **C6（経済性）と正面衝突する**。具体策は無い。

## 3. 独立レビューが追加で見つけた重大欠陥（人間レビューには無かった）

severity=high の8件のうち、とくに効くもの:

| # | 欠陥 | なぜ効くか |
|---|---|---|
| ~~H1~~ | ~~**CVE設定例が自己矛盾**~~ | **❌ 誤検出だった。§3.1 参照** |
| H2 | **`acceptance[].run` がコマンドインジェクション経路** | LLM 出力の任意コマンド文字列を実行する設計と、§8.3「定義済みコマンドのみ実行」が**衝突している** |
| H3 | **append-only JSONL の原子性が未定義** | 同時追記のインターリーブ・fsync・クラッシュ途中書込み・重複排除が無い。**クラッシュ耐性の基盤が未成立** |
| H4 | **証拠が成果物に束縛されていない** | stdout/exit code しか固定せず、commit hash・環境ハッシュ・入力を含まない。**どの成果物の証拠か保証できない** |
| H5 | **`cites` の意味的対応を検証していない** | 無関係な exit 0 証拠を引用しても finding が通る。スキーマは存在を強制できても妥当性は強制できない |

**H2 と H4 は設計の根幹に関わる。** とくに H4 は、証拠に基づく裁定という中心主張の前提が
崩れうる指摘である（証拠と成果物の対応が保証されないなら、裁定は空を切る）。

### 3.1 ★H1 は誤検出だった — そして、それ自体が本設計の正しさの証拠

独立レビューは「`shell: bash` なのに Python の Windows 絶対パスを書いており、
**サンプル自体が動かない可能性**がある」と severity=high で指摘した。

**実機で確認したところ、動いた。**

```console
$ "<home>/AppData/Local/hermes/.../python.exe" -c "import sys;print('OK',sys.version.split()[0])"
OK 3.11.11
$ git --version
git version 2.41.0.windows.1
```

git-bash は Windows 絶対パスをそのまま解釈するため、`shell: bash` と Windows パスの併記は矛盾しない。
レビュアは**実行できない状態で推測し、断定的に high と判定した**。

> **この誤検出は、E-4 とまったく同じ構造である。**
> レビュアが自分の手元で確認できないことを、成果物の欠陥として報告した。
>
> そして本設計の §7.2 に通せば、この指摘は正しく処理される:
> **H1 の主張には CVE 由来の証拠 ID が付いていない → `advisory` 止まりで、`fail` にはならない。**
> 逆に H2〜H5 は文書内の記述を根拠にしており、証拠として成立している。
>
> **つまり「証拠を引けない指摘は裁定に使わない」という規律は、
> 今回の独立レビュー自身に対しても正しく機能した。** N=1 の追加事例ではあるが、
> 設計の中心命題を支持する方向の事例である。

**ただしこれは §2.2 の結論を変えない。** H1 が誤検出でも、H2〜H5 は有効であり、
「実証済み」の書きすぎと acceptance の質の問題は依然として認めるべき指摘である。

## 4. 反論する点（1点のみ）

独立レビューは §0 の中心命題「本質的な難所は連携でなく判定の信用」も過大主張として挙げた。
理由は「E-4 は一事例で、並列連携・長期状態・統合との比較測定がない」。

**部分的に受け入れるが、全面撤回はしない。**

- 認める: 「**本質的**」「難所は連携で**はなく**」という**強い一般化**は N=1 では支えられない。
- 反論: E-4 は「連携は成功していた（ファイルは渡り、レビューは走った）のに、判定が誤った」
  という**構造を持つ事例**である。連携の配管が正しく動いた上で判定だけが壊れたことは、
  「判定は連携とは独立に壊れうる」ことを示す。これは N=1 でも意味のある**存在証明**である。
- 妥当な言い方: 「判定の信用は、連携の配管とは**独立に壊れる**。そして見落とされやすい」。
  「連携より重要」ではなく「連携ができても解決しない」が正確。

## 7. この一件から得た教訓（設計プロセスへの反映）

1. **自分の設計の規律は、自分の設計書にも適用する。**
   「Reviewer は別ベンダー」と書きながら自己採点していたのは、設計思想の不徹底だった。
2. **「実証済み」は、統合経路を通したときだけ使う。**
   合成入力の単体テストを「実証」と呼んだのは、自分に対する誇張だった。
3. **自己採点は 92 点、独立レビューは unsound。この乖離幅そのものが教訓。**
   LLM に自分の成果物を採点させると甘くなる。**別ベンダーの独立レビューは安価で効果が大きい**
   （今回1回で high 8件を検出）。これは本設計の §6.1 が正しいことの傍証でもある。

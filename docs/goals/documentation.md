# ドキュメント構造のゴールと評価方法

このファイルは「super-agent/src のドキュメントをどう構成すべきか」を定める。
設計本体（docs/spec.md）と同様、**ゴールを先に決め、後から構造を都合よく動かさない**
ために、構造そのものの評価基準を定める。

---

## 1. ゴール（ドキュメント構造が満たすべきこと）

### 1.1 一眼でわかる固定名

| 固定名 | 役割 | 置き場 |
|---|---|---|
| `README.md` | 入り口。何か・現状・目録へのリンク | リポジトリ直下（src/） |
| `docs/spec.md`（仕様） | 設計の**現在の正**（ARCHITECTURE の後継・正アンカー） | docs/ |
| `docs/plan.md`（実装計画） | 実装の順序と進捗 | docs/ |

> 命名は英語/日本語どちらでもよいが、**役割で固定**し、ファイル名からカテゴリが
> 一目で分かること。実証ログ等はフォルダで括る。

### 1.2 分類とフォルダ

```
docs/
  README.md            ← 入り口（src/ 直下にも同じもの/リンク）
  spec.md              ← 仕様（設計の正）
  plan.md              ← 実装計画
  catalog.md           ← 手引き（全ドキュメントの目録）
  goals.md             ← ゴールと評価方法（このファイル）
  evidence/            ← 実測・実証の証跡（時系列・追加型）
    YYYYMMDD-<topic>.md
  design-notes/        ← 設計上の決定・論考（ADR 的）
    <topic>.md
```

### 1.3 分類の原則

- **仕様（spec）**：システムが「今どうあるべきか」の単一正源。時間が経っても追記・訂正で
  唯一の真となる。実験の経緯は載せない。
- **証拠（evidence/）**：いつ・何を・どう実測したかの**追加型ログ**。上書きせず追記。
  ファイル名に日付を入れ、検証可能性を残す。
- **論考（design-notes/）**：特定論点の深掘りや決定の理由。証拠と違い「考え」を記す。
- **計画（plan）／使い方（usage）**：操作レベルの手順。仕様から独立して更新できる。

### 1.4 スコープ

| 含む | 含まない |
|---|---|
| 設計・仕様・目録・実装計画・使い方・実証ログ・論考 | ソースコード自体のコメント |
| 設計の正とその根拠 | ベンダーCLIの内部仕様（外部ドキュメントへ） |

## 2. 評価方法

### 2.1 採点ルーブリック（100点）

| # | 評価軸 | 配点 | 満点の条件 | 0点の条件 |
|---|---|---|---|---|
| D1 | **固定名の存在** | 15 | README/spec/plan が固定名で存在し、役割が明確 | 名前がバラバラで役割不明 |
| D2 | **分類の一貫性** | 20 | 全ドキュメントが folders（evidence/design-notes）に属し、命名規則が統一 | カテゴリなく散乱 |
| D3 | **目録（catalog）** | 15 | 全ドキュメントを網羅する手引きがあり、概要と場所が書かれている | 目録が無い |
| D4 | **単一正源（spec）** | 20 | 設計の「今の正」が1ファイルに集約され、実証経緯と分離 | 正源が複数に散る |
| D5 | **検証可能性の保持** | 15 | 実証ログが日付付きで残り、いつ何を確認したか辿れる | 主張だけで根拠が消えている |
| D6 | **具体化（リンク整合）** | 15 | 相互リンクが切れておらず、古いパスを指していない | リンク切れ・デッド参照多数 |

### 2.2 致命項目

- **F-D1**: 入り口（README）が無い、またはどこから読めばよいか不明。
- **F-D2**: 仕様（spec）が無く、設計の正が複数ファイルに散っていて「今の正」が一読で分からない。

### 2.3 合格線

**85点以上、かつ致命項目ゼロ。** 70点未満は不合格として再構成。

### 2.4 反復手順

```
構造案を作る → ルーブリックで採点 → 失点を潰す → 合格まで繰り返す
```

各版の点数は `docs/goals/documentation.md` または catalog に残す。

# N=3 実測 と 大きな差分への対処

- 実施日: 2026-08-06
- 動機: 独立レビューの指摘「検証がN=1」「大きな差分でC6と衝突する具体策が無い」への回答
- 場所: `probe/n3/`（本ディレクトリは成果物ではなく**実験の証跡**）

---

## 0. 何が変わったか（要約）

| 項目 | 前回 | 今回 |
|---|---|---|
| 標本数 | N=1（16行1ファイル） | **N=4**（16行 / 2ファイル / 3ファイル相互依存 / **42ファイル**） |
| CVE | 手動 `python fizz.py` | **`cve.py` として実装**（証拠に tree_hash を束縛 = H4対応） |
| 裁定 | 証拠なき指摘は破棄 | **`advisory` として保持**（裁定には使わない = 独立レビュー指摘への対応） |
| 大きな差分 | 具体策なし | **`brief.py` 実装。9,612→1,706 tok（82%削減）で正答維持** |

## 1. 題材（意図的に難易度を上げた）

| Case | 規模 | 埋め込んだ問題 | 狙い |
|---|---|---|---|
| A（前回） | 16行 1ファイル | なし（正しいコード） | 偽fail が消えるか |

## 2. Case B — 「acceptance が天井」を実測で確認した

CVE 実行結果: **`4 passed`（exit 0）**。しかしコードには問題がある。

2ベンダーに同一簡報（read-only, 全文埋め込み 1,046 tok）でレビューさせた:

| レビュア | opinion | 指摘 |
|---|---|---|
| codex | `fail` | Money が bool を受理 / **Money が可変で履歴を書き換えられる** |
| claude | `pass` | **`is_balanced()` が恒真**（テストが無意味）/ `__eq__` に `__hash__` が無い |

### 指摘の真偽を CVE で検証した（推測しない）

```console
Money(True).cents = True                       ← codex 正しい
balance after mutating Money: 9999.99          ← codex 正しい（履歴が壊れる）
is_balanced() は post() の制約から常に True     ← claude 正しい
```

**3件とも真**だった。とくに claude の「テストが恒真」は、
**独立レビューが指摘した「exit 0 は正しさを意味しない」の実例**である。

> ### ここが本質
> `4 passed` は「正しい」を意味しなかった。
> **CVE は「テストが通ったこと」しか保証しない。「テストが十分か」は保証しない。**
> これは設計の限界として `ARCHITECTURE.md` §7.2 に明記済み。
> 一方で、**レビュアはテストが拾えない欠陥を実際に拾えた**（可変性・恒真テスト）。
> つまり CVE とレビュアは代替関係ではなく**補完関係**である。

### 2ベンダーの意見が割れても、機械裁定は同一だった

| | codex(opinion=fail) | claude(opinion=pass) |
|---|---|---|
| **裁定結果** | **`pass`** | **`pass`** |
| advisory | 2件保持 | 2件保持 |

**レビュアの opinion が正反対でも、裁定は一致した。** これが「判定の信用」の実装である。
そして**指摘は1件も失われていない**（`advisory` に全件保持）。

## 3. Case C — 実failは正しく fail になる

`retry()` に `range(attempts - 1)` を仕込んだ（最終試行が実行されない）。

- CVE: **exit 1**、`1 failed, 4 passed`
- codex（**予算圧縮した簡報 729 tok**）:
  > (high) retry() invokes the function only **attempts - 1** times, so the final permitted attempt is never made. cites=`['E-1']`
- 裁定: **`fail`** (`acceptance failed: ['E-1']`)

**根本原因を正確に特定した。** しかも全ソースを渡さず、証拠＋変更ファイルのみで。

## 4. Case D — 大きな差分への対処（本題）

42ファイル・38,450字（**素朴に全文投入すると ~9,612 tok**）。
`pkg/mod00.py` のシグネチャを変更し、呼び出し側を壊した。

### 4.1 対処法: 決定関連性による階層化 + 予算内での順序付き劣化

`brief.py` に実装。**落とす順番を固定**することが要点:

| 階層 | 内容 | 落とす順 |
|---|---|---|
| **T0** | **証拠の末尾**（CVE実行結果） | **絶対に落とさない**（これが無いと裁定不能） |
| **T1** | 変更されたファイル本体 | 2番目に守る |
| **T2** | 未変更ファイルの**シグネチャのみ**（`ast` で抽出、本体なし） | 3番目 |
| T3 | 未変更ファイルの全文 | **最初に捨てる**（贅沢品） |

さらに、落としたものは `=== OMITTED (budget) ===` として**簡報に明記**し、
「省略部分について推測するな」と指示する。**黙って隠さない**ことが安全性の要。

### 4.2 実測結果

| 方式 | トークン | 削減 | 裁定 | 根本原因の特定 |
|---|---|---|---|---|
| 素朴（全42ファイル投入） | ~9,612 | — | — | （未実施） |
| **予算2000** | **1,836** | **-81%** | `fail` | ✅ 正確 |
| **予算700**（34ファイル省略） | **820** | **-91%** | `fail` | ✅ **正確** |

予算700での指摘:
> (high) The smoke test fails because `op0_0` requires a `scale` argument, while the test calls it with only `(1, 2)`. cites=`['E-1', 'CHANGED pkg/mod00.py: ...']`
> (med) The added `scale` parameter is **not used** in the implementation, indicating an incomplete API change.

**34ファイルを省略しても、正しい根本原因と追加の設計指摘まで出した。**

### 4.3 なぜ効くのか（原理）

**大きな差分でも、判定に必要な情報は差分に比例して増えない。**
判定に効くのは「① 何が失敗したか（証拠）」「② 何を変えたか（変更差分）」であり、
①は差分の大きさと**ほぼ無関係**、②は差分に比例するが**変更部分だけ**でよい。
未変更コードは「呼び出し先の形」さえ分かればよく、それは**シグネチャで足りる**（本体は不要）。

> 逆に言えば、**素朴な全文投入は、判定に寄与しない情報にトークンを払っている**。
> C6（経済性）と C2（判定信頼性）は、正しく階層化すれば**トレードオフではない**。

### 4.4 この方式の限界（正直に）

- **T2 をシグネチャに落とすと、本体にしかない欠陥は見えない。**
  Case B の「Money が可変」は本体を読んで初めて分かる指摘であり、
  もし `money.py` が T2 に落ちていたら**検出できなかった**。
- したがって「予算を絞るほど advisory の質が落ちる」というトレードオフは**残る**。
  消えたのは「大きな差分では判定そのものが不可能になる」という問題であって、
  「レビューの網羅性が予算に依存する」問題ではない。
- **推定トークンは `chars/4` の概算**。実トークン数は未計測（ベンダーAPIの usage 取得は未実装）。

## 5. 実装した H4 対応（証拠と成果物の束縛）

独立レビュー指摘 H4「証拠がどの成果物に対応するか保証できない」に対応。

`cve.py` は全対象 `.py` の内容から `tree_hash` を計算し、証拠バンドルと裁定結果の両方に埋め込む。

```
Case B tree_hash: 7b8f8ae90f23dce4
Case C tree_hash: 8dcf0f997d4e07b1
Case D tree_hash: b12a8e0019c93646
```

裁定結果が**どの状態のコードに対する判定か**を機械的に追跡できる。

## 6. 副産物: 新しいベンダー非対称性（A-5）

| ベンダー | `--json-schema` の渡し方 |
|---|---|
| claude | **スキーマJSON本文をインラインで**渡す（ファイルパスを渡すと `not valid JSON` エラー） |
| codex | **ファイルパスを** `--output-schema` に渡す |

同じことをするのに引数の意味が違う。アダプタ宣言（§4.1）で吸収すべき差分として記録。

## 7. CVE 自身の故障も実測できた

Case B 初回実行時、CVE の python パスを相対パスで書いており起動に失敗した:

```json
{"cve_ok": false, "probes": [{"exit_code": null, "error": "ENOENT: [WinError 2] ..."}], "evidence": []}
```

**このとき裁定は `fail` ではなく `environment_error` になる。**
成果物は無傷なので責めない——G2 が設計通り機能した（今度は実装で確認）。

## 8. 結論

| 主張 | 更新後の状態 |
|---|---|
| 実行と判定の分離で偽failが消える | **N=4**（16行 / 2 / 3 / 42ファイル）。ただし「レビュア環境起因の1経路」限定は変わらず |
| 裁定4分類が機能する | **実CVE + 実LLM で確認**（合成入力でなくなった） |
| レビュア意見が割れても裁定は安定 | **実測**（codex `fail` / claude `pass` → どちらも `pass`） |
| 証拠なき指摘の破棄 → advisory 化 | **実装・実測**（指摘を失わずに裁定の独立性を維持） |
| 大きな差分でも予算内で判定できる | **実測**（-81%〜-91% で正答維持） |
| acceptance が正しさの天井 | **実例で確認**（`4 passed` でも可変性バグと恒真テストが残存） |

**「N=1」と「大きな差分の具体策なし」という2つの指摘は解消した。**
一方で「acceptance の質が天井」は**解消していない**——むしろ Case B で実例が出た。
これは CVE では解けない問題であり、`ARCHITECTURE.md` §7.2 の既知欠陥のまま残る。

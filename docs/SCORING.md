## v1（素朴案）— 52点 / 致命2件 → **不合格**

**v1の内容**: 5層構造（基盤/アダプタ/統制/共有メモリ/通信）。
Karo相当のオーケストレータがタスクを分解し、実装者に配り、レビュア役のエージェントが
「動かして確認して合否を返す」。共有メモリに全決定を書く。

| 軸 | 点 | 失点理由 |
|---|---|---|
| C1 実測整合性 | 9/15 | 能力表は実測に基づくが、A-2/A-3を設計に反映していない |
| C2 判定信頼性 | **2/20** | **レビュアの verdict をそのまま採用。E-4 の偽failが再発する** |
| C3 交換可能性 | 7/10 | 宣言化の方針はあるが、セッションID採番差(A-1)で破綻 |
| C4 回復 | 6/10 | 状態はファイルにあるが、割当が「代入」なので担当者が落ちると放置される |
| C5 メモリ | 5/10 | 「共有メモリに全部書く」。ベンダー内記憶(E-2b)との関係が未定義 |
| C6 経済性 | 3/10 | コストへの言及が薄い。E-5の13.8万トークンを織り込んでいない |
| C7 人間 | 6/10 | 承認ゲートはあるが、上げる/上げないの線引きが無い |
| C8 具体性 | 9/10 | スキーマは書けている |
| C9 自己適用 | 5/5 | 可 |
| **合計** | **52** | |

**致命項目**
- **F2 抵触**: レビュー結果を無検証で採用 → E-4 が構造的に再発する
- **F1 抵触**: 再開時も起動時と同じ権限フラグで動く前提 → A-2 で否定済み

**判断**: C2 が壊れている限り、他を磨いても意味がない。**設計の中心を差し替える。**

## v3（現行）— 92点 / 致命0件 → **合格**

**v2からの変更**:
1. **判定を4分類に拡張** — `pass` / `fail` / `environment_error` / `judgment_unavailable`。
   「成果物が悪い」と「判定できなかった」を分離（§7.2）。→ C2 を満点へ
2. **証拠なき指摘は破棄**する裁定規則を明記。`opinion_verdict` に改名し、意見であることを設計上明示 → C2
3. 台帳を **append-only JSONL** に変更。派生ビューは再生成可能に → C4 満点
4. **簡報（briefing）** を導入し、役割ごとに渡す文脈を限定。E-5 を根拠として明記 → C6
5. 「**記憶は最適化であって正しさの前提にしない**」を原則として明記 → C5
6. Reviewer に「別ベンダー強制」「read-only強制」の2制約を追加
7. §11「明示的に否定する設計」、§12「未解決論点」を追加

| 軸 | 点 | 根拠 |
|---|---|---|
| C1 実測整合性 | 15/15 | 全前提が EVIDENCE.md の E-1〜E-5 / A-1〜A-4 に紐づく |
| C2 判定信頼性 | **20/20** | CVE + 3段分離 + 4分類 + 証拠引用強制。§7.2 で E-4 を通し pass を確認 |

| C5 メモリ | 9/10 | 四層 + 役割分担明記。−1: ベンダー内記憶の失効検出は未設計 |
| C6 経済性 | 9/10 | 簡報・予算・トークン正規化。−1: 価格表の更新運用が未定義 |
| C7 人間 | 10/10 | 上げる/上げない表。エージェント数に対し負荷が増えない構造 |

## 反復で何が変わったか（要約）

| | v1 | v3 |
|---|---|---|
| 判定の主体 | レビュア（LLM） | **CVE（機械）+ 規則** |
| レビュアの権限 | 実行可 | **read-only 強制** |
| 不合格の種類 | 1種 | **4種**（環境障害・判定不能を分離） |
| 台帳 | 上書き | **append-only** |
| 割当 | 代入 | **期限付きリース** |
| メモリ | 全部共有 | **共有するもの/しないものを分離** |
| 点数 | 52（致命2） | **92（致命0）** |

**最大の転換点**: v1→v2 で「レビュアに合否を訊く」のをやめたこと。
これは実測 E-4 が無ければ気づけなかった。**設計の前に実測した価値がここに出ている。**
